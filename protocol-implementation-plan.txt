1. SCOPE AND THE CUTOVER DECISION
================================================================================

[C-01] CLEAN CUTOVER -- THIS OVERRIDES THE PROPOSAL
    The user has ruled that backward compatibility is NOT a consideration.
    Nothing migrates. This supersedes these parts of protocol-revision.txt:

        [V-02] "Existing v2 rooms remain usable through a legacy compatibility
               implementation"                                     -> DROPPED
        [V-04] Migration / "Create v3 replacement" flow             -> DROPPED
        [S-01] "Existing profile, friends, messages, keys, favorites,
               invitations, and preapprovals receive explicit migration rather
               than deletion"                                      -> DROPPED
        [I-07] "Keep v2 room records on the legacy path"            -> DROPPED
        [Q-09] Compatibility test                                   -> DROPPED
        [Q-10] Storage migration test              -> REPLACED, see [Q-10']

    Consequences, all intended:
      - No `protocolVersion` branch anywhere in the code. There is one protocol.
      - No legacy RoomSession, no v2 packet types, no v2 verifiers.
      - v2 wire constants, domain tags and KDF strings are deleted, not kept
        alongside v3 ones.
      - A fresh IndexedDB database is used. See [C-02].
      - Existing users lose local history, friends, favourites and their
        identity keypair on first run of the new build. Accepted.

[C-02] STORAGE: NEW DATABASE, NO UPGRADE PATH
    Use a new database name `AirComicDB_v3` at version 1, with a fresh
    `onupgradeneeded` that creates every store from scratch. Do NOT write
    migration branches against `AirComicDB_v2`.

    Optionally delete the old database on first successful open of the new one
    (`indexedDB.deleteDatabase('AirComicDB_v2')`) so stale data does not sit in
    the browser forever. Do this AFTER the new DB opens successfully, never
    before, and never as a precondition.

    Because the profile store starts empty, a new identity keypair is generated
    on first run, so participantId changes and friends lists start empty. This
    is the accepted meaning of "clean cutover". Nothing in the code should try
    to detect or repair the old state.

[Q-10'] Replacement acceptance test for [Q-10]
    First run against a browser profile that already holds `AirComicDB_v2`
    completes normally: the new DB is created, a new identity is generated, the
    app is usable, and no error surfaces from the presence of the old database.

[C-03] What is NOT in scope for this work
    - Comic rendering, avatar/backdrop parsing, emotion engine, layout: untouched.
    - MLS or any group ratchet. [PR-08]/[O-16] defer this explicitly.
    - Replacing RSA-OAEP with ECDH/HPKE. [O-15] defers this explicitly.
    - Blob/asset storage for images and audio. [P-04] and [W-07] describe the
      shape; no such feature exists today and none is being added. Implement the
      size limits that forbid embedding large assets, and nothing more.
    - Padding / cover traffic. [N-05] defers this.
    - NIP-29 relay-managed moderation. [PU-06] defers this.
    - Push notifications. The service-worker scaffolding stays as it is.

2. LOCKED DECISIONS
================================================================================

These resolve ambiguities and internal gaps in protocol-revision.txt. They are
settled; do not re-litigate them during implementation. Each says why.

[L-01] Wire naming stays `airthread/3`
    Per [V-01] and [O-20]. All domain tags, KDF info strings and extension names
    use `airthread`. The product is still AirComic. No renaming pass.

[L-02] routingKey is fed into routingTag as its Base64URL text
    [T-04] writes `routingTag = Base64URL(SHA-256("airthread-v3-room:" +
    routingKey))` without saying how the 256-bit routingKey enters a string
    concatenation. Ruling: routingKey is Base64URL-encoded first, then
    concatenated as text, then the whole string is UTF-8 encoded and hashed.
    Pin this in a single helper so it cannot drift.

[L-03] Per-room Nostr key derivation uses jwk.d as raw HMAC key material
    [T-06] says `HMAC-SHA-256(key = raw private ECDSA scalar material, data =
    "airthread-nostr-room-v3:" + routingTag)`. Ruling: the scalar is the P-256
    private key JWK's `d` member, Base64URL-decoded to its 32 raw bytes, imported
    as an HMAC-SHA-256 key. Rejection loop on out-of-range scalars re-hashes as
    `HMAC(key, prevSeed || counterByte)` with counter starting at 0, max 32
    attempts, then throw. This mirrors the existing v2 helper's structure
    (crypto.ts:1341 deriveNostrSecretKey) so the shape is familiar.

[L-04] A GenesisPacket is added; the proposal requires one but never defines it
    [M-01] refers to "the room genesis packet" and [PR-04] requires every epoch
    transition to name a validated parent, so the chain needs a root. Define
    `RoomGenesisPacket` -- see spec [X-07]. Epoch 1's parent is the genesis
    packet id.

[L-05] Genesis and the epoch chain need stable discoverability
    [T-03] gives immutable packets `d = packetId`, which makes them
    unlistable except by scanning the routing tag. A joiner needs the genesis
    packet and the current epoch head without replaying the entire room.
    Ruling:
      - Genesis is published with the stable tag `d = "genesis:" + routingTag`
        so it is retrievable in one query, and republished verbatim (same
        packetId, re-signed Nostr event) onto every new route after a
        capability rotation.
      - Control packets (`packetClass: 'control'`) carry NO `expiration` tag,
        so relays are asked to keep them for the life of the room. The
        authoritative durable copy is still the local `membershipHeads` store.
      - The epoch chain is rebuilt by querying the routing tag filtered to
        control packets and walking from genesis. Rekeys are rare, so this is
        cheap. Do NOT add a mutable "current head" pointer event: it would be
        forgeable and racy, and the chain rules already give a deterministic
        answer.

[L-06] Retention class for control packets overrides [T-09]
    [T-09] lists "chat/control history 30 days". Ruling: chat gets 30 days;
    control gets no expiration tag, per [L-05]. Membership must remain
    reconstructible longer than chat.

[L-07] Presence capability is ONE per user, rotated on revoke -- not one per contact
    [N-01] says "Each accepted contact MAY receive a distinct capability" and
    then "Revoking a contact rotates capabilities for the remaining authorized
    contacts". Per-contact capabilities would require publishing one presence
    event per contact every republish interval, which scales badly and gains
    little. Ruling: a single presence capability per user, with a generation
    counter, distributed sealed to each authorized contact, rotated and
    redistributed to the remaining contacts on revocation. One presence event
    per republish, exactly as today. See spec [X-11].

[L-08] Inbox tags remain derived from participantId
    [N-01] changes PRESENCE tags to capabilities. It does not change inbox tags,
    and [N-05] explicitly accepts that "inbox tags and event timing remain
    observable". Ruling: `inboxTag = Base64URL(SHA-256("airthread-inbox-v3:" +
    participantId))`, same construction as v2 with a v3 domain separator. This
    preserves the ability to send a sealed invitation to anyone whose contact
    card you hold, which is how the friend relationship is bootstrapped in the
    first place. Flagged for confirmation as [U-02].

[L-09] Public room presence carries no inner application signature
    [PU-04] shows a `"signature": "<application signature>"` field on a record
    whose stated purpose is pseudonymity. An ECDSA identity signature there
    would defeat the pseudonymity; a signature by the room-scoped Nostr key
    would duplicate the Nostr event signature. Ruling: drop the inner
    signature. `presenceId` IS the room-scoped Nostr public key (hex), the
    Nostr event's Schnorr signature is the authentication, and occupancy is
    counted as distinct valid unexpired publisher pubkeys. Note that in a public
    room the same room-scoped key also publishes that user's messages, whose
    envelopes carry the real participantId -- so this is pseudonymity ACROSS
    rooms, not within one. Document that in the UI copy.

[L-10] `isSecretMissing` / MissingSecretDialog is retained
    Joining by `?id=` with no `#secret=` is still possible (a truncated or
    stripped link). In v3 the consequence is stronger: without the secret the
    client cannot even compute the routing tag, so it sees nothing at all rather
    than sitting unapproved on a mesh. Keep the dialog, update the copy.

[L-11] Public rooms are unencrypted end to end
    Per [P-01]/[PU-01]. `derivePublicTransportKey` and the whole `public-v2` key
    record are deleted. Public envelopes carry `iv: ""` and
    `data = Base64URL(UTF8(canonical payload))`. The publicJoinToken survives
    only as the input to publicRoomId and as the "you have the link" token; it
    is no longer key material.

[L-12] Message send is persist-then-publish, and optimistic in the UI
    Per [D-01]. The local message record appears immediately with state
    `pending`, flips to `relayed` on quorum, `failed` after the retry budget is
    exhausted. The UI must show this; see phase 8. `sent` never means "read".

[L-13] Deduplication is `(convId, packetId)` with a content hash
    Per [D-02]. contentHash = Base64URL(SHA-256(exact serialized RoomEnvelope
    bytes as published)). A second arrival with the same key and a different
    hash is a collision: keep the first, count it, never render the second.

[L-14] One RelayPool singleton owns every WebSocket
    Per [T-01]. PresenceService and PublicDirectoryService stop opening their
    own sockets and become clients of the pool. This removes the current
    situation where three subsystems independently open sockets to the same
    five relays.

[L-15] Trystero keeps its own relay sockets
    Trystero opens its own connections and cannot be pointed at the RelayPool
    without forking it. That is acceptable because WebRTC is now optional, at
    most one private room at a time [R-03], and it is off by default when
    unavailable. Do not attempt to unify the two.

[L-17] The 20-member figure is a SOFT WebRTC threshold, not a protocol cap
    RESOLVES [U-05], and OVERRIDES [R-04] of protocol-revision.txt, which said
    "Private rooms have a protocol membership limit of 20 participants."
    The user has ruled: there is no protocol membership cap. 20 is only the
    point past which WebRTC acceleration stops being attempted and the room
    runs on Nostr alone, which it can always do.

    Consequences:
      - Epoch-chain validation does NOT reject a members array for being
        larger than 20. See the amended clause (f) in [X-07].
      - There IS still a hard structural bound, imposed by the envelope size
        limit rather than by policy. A RekeyPacket carries one RSA-OAEP-2048
        slot per member: 256 bytes -> 344 base64url chars, plus a 43-char
        participantId key and JSON punctuation, ~440 bytes per member once the
        members array is counted too. Against MAX_ENVELOPE_BYTES of 60 KiB that
        allows roughly 137 members, so the validator caps members at
        MAX_PRIVATE_MEMBERS_HARD = 128 with the envelope limit as the reason.
        Exceeding it is a structural rejection, not a membership policy.
      - The accelerator threshold is WEBRTC_MEMBER_THRESHOLD = 20 [W-01].
      - No "room is full" UI state. Approve is never disabled for headcount.
      - Acceptance test [Q-05]'s "over-20 membership" case is replaced by
        "over-128 membership is structurally rejected", and a new case: a room
        of 21+ members keeps working with accelerationStatus 'unavailable'.

[L-16] Delete rather than deprecate
    Every v2-only construct listed in section 7 is deleted in the phase that
    replaces it. Do not leave dead code behind a flag.

[U-01] Add a test framework?  (blocks phase 1, but only for the test files)
    The epoch-chain validator, bounded structural validator, dedup, quorum and
    all KDFs are pure functions, and getting them wrong is silent and severe.
    Recommendation: add Vitest as a devDependency with a `npm test` script and
    unit tests for src/services/v3/crypto*, validators and the chain rules.
    Node 24 provides WebCrypto, so no browser environment is needed.

ANSWER: add it

[U-02] Confirm inbox tags stay participantId-derived  (blocks phase 6)
    See [L-08]. The alternative -- capability-gated inboxes -- would mean you
    can only be invited by someone you have already exchanged capabilities with,
    which changes how friends are bootstrapped.

ANSWER: participantId-derived

[U-03] Default relay list and user configurability  (blocks phase 2)
    [T-01] requires the relay list to be user-configurable. Today it is a
    hard-coded list of 5 preferred + 6 trystero defaults (protocols.txt [T-05]).
    Questions: keep the same 5 as the shipped default? Where does the user edit
    the list -- a new section in the Security dialog, or a new Relays dialog?

ANSWER: keep the current 5 preferred relays as the default set, add editing to the existing SecurityDialog, persist in the new `settings` store.

[U-04] Locked vault mode -- now or later?  (blocks phase 7 sizing)
    [S-02] defines Convenience mode (today's behaviour) and Locked vault mode
    (Argon2id-wrapped secrets). Locked vault needs a passphrase prompt on every
    cold start, a new dependency for Argon2id, and a recovery story.
    Recommendation: implement Convenience mode only in this pass, but lay the
    store shape out so vault mode is additive (a `vault` store and a
    `storageMode` field that is always 'convenience' for now), and put the
    honest disclosure text in the Security dialog.

ANSWER: convenience only, with the disclosure text.

[U-05] Private room member cap UI  (blocks phase 8)
    [R-04] sets a hard protocol cap of 20 private members. What should the UI do
    at the cap -- grey out approve with a reason, or hide the prompt?

ANSWER: SOFT limit of 20; WebRTC is only used for the active private room, for convenience; if exceeded, falls back to Nostr

[X-02] Key derivations -- src/services/v3/keys.ts
--------------------------------------------------------------------------------
Identity keypairs are UNCHANGED from v2: RSA-OAEP 2048 (SHA-256) for key
transport, ECDSA P-256 (SHA-256) for signatures, participantId =
Base64URL(SHA-256(SPKI of the signing key)). Reuse the existing generator and
the normalizePublicKey / canonicalStringify helpers from crypto.ts verbatim.

Room secret: 32 random bytes (256 bits) Base64URL, per [PR-01]. Note this is a
change from v2's 128 bits.

All room derivations are HKDF-SHA-256 with
    IKM  = UTF-8(roomSecret.trim())
    salt = SHA-256(UTF-8(<saltPrefix> + convId.trim().toLowerCase()))
    L    = 256 bits

    purpose        saltPrefix                    info
    -----------    --------------------------    -------------------------------
    root control   "airthread-v3-root:"          "airthread-private-root-key-v3"
    routing        "airthread-v3-routing:"       "airthread-private-routing-v3"   [T-04]
    webrtc room    "airthread-v3-webrtc:"        "airthread-private-webrtc-room-v3"   [W-02]
    webrtc pass    "airthread-v3-webrtc:"        "airthread-private-webrtc-password-v3"   [W-02]

    root control -> AES-GCM CryptoKey (control packets only, never chat) [PR-01]
    routing      -> raw bits, then per [L-02]:
                    routingKey = Base64URL(bits)
                    routingTag = Base64URL(SHA-256(UTF-8(
                        "airthread-v3-room:" + routingKey)))
    webrtc room  -> Base64URL, passed to Trystero as roomId
    webrtc pass  -> Base64URL, passed to Trystero as password

Public rooms:
    publicRoomId = Base64URL(SHA-256("airthread-public-room-v3:" +
                                     convId.toLowerCase() + ":" + publicJoinToken))
    routingTag   = publicRoomId                                          [T-05]
    No transport key. No signalling password beyond what Trystero needs, and
    public rooms never start Trystero at all.                            [R-03]

Per-room Nostr publishing identity                        [T-06], ruled by [L-03]
    dBytes = Base64URL-decode(signingPrivateKeyJwk.d)      // 32 bytes, P-256 scalar
    hk     = importKey('raw', dBytes, {name:'HMAC', hash:'SHA-256'}, false, ['sign'])
    seed0  = HMAC(hk, UTF-8("airthread-nostr-room-v3:" + routingTag))
    for i in 0..31:
        if 0 < BE(seed_i) < secp256k1_n: return seed_i
        seed_{i+1} = HMAC(hk, seed_i || byte(i))
    throw

    Cache derived room keys in memory keyed by routingTag; the HMAC is cheap but
    this runs on every publish.

Inbox / presence tags
    inboxTag        = Base64URL(SHA-256("airthread-inbox-v3:" + participantId))   [L-08]
    responseTag     = inboxTag + "~r"
    quickMsgTag     = inboxTag + "~qm"
    presenceCapTag  = Base64URL(SHA-256("airthread-presence-cap-v3:" + capability))  [L-07]

    The user's own inbox Nostr identity: derive as [T-06] with
    routingTag replaced by the literal "inbox:" + participantId, so the inbox
    publisher key is stable but distinct from every room key.

Directory publishing identity                                            [PU-02]
    Derive as [T-06] with routingTag = publicRoomId. Stable per public room,
    which is what makes NIP-33 replacement work across reloads, and isolated
    from presence and other rooms. This fixes v2 [O-08].

[X-03] RoomEnvelope -- src/services/v3/envelope.ts
--------------------------------------------------------------------------------
Exactly the shape in [P-01]:

    interface RoomEnvelope {
      protocol: 'airthread/3'
      extension: 'airthread/3-nostr-transport'
      type: 'room_envelope'
      convId: string
      packetId: string          // uuid, globally unique, also the Nostr d tag
      roomMode: 'private' | 'public'
      packetClass: 'chat' | 'control' | 'metadata' | 'system'
      keyId: string             // 'epoch-N-xxxxxxxx' | 'root-v3' | 'public-v3'
      senderId: string          // participantId
      senderSigningPublicKey: string
      timestamp: number
      iv: string                // base64url 12 bytes, or '' for public
      data: string              // base64url ciphertext, or base64url(UTF8(json))
      signature: string
    }

    AAD = "airthread/3:" + convId + ":" + packetId + ":" + roomMode + ":" +
          packetClass + ":" + keyId + ":" + senderId + ":" + timestamp   [P-02]

    Signature over AIRTHREAD_ROOM_ENVELOPE_V3: + canonicalStringify(envelope
    minus signature) -- so it covers the ciphertext.                     [P-02]

    Receive order is mandatory and must not be reordered              [P-02]:
      1. byte-size check against MAX_ENVELOPE_BYTES
      2. JSON.parse
      3. bounded structural validation [X-04]
      4. derive senderId from senderSigningPublicKey; reject on mismatch
      5. verify the envelope ECDSA signature
      6. check convId + roomMode match the room, and that the packet arrived on
         that room's routing tag
      7. timestamp acceptance [D-04]
      8. dedup on (convId, packetId) [X-06]
      9. authorization: is senderId a member of the canonical epoch applicable
         at packet.timestamp?  [M-02]
     10. only now decrypt and parse `data`

    Steps 1-5 must complete before any decryption is attempted. Never decrypt to
    decide whether to verify.

RekeyPacket v3
    { type:'key', protocol, convId, packetId, keyId, epoch,
      parentPacketId, parentKeyId,
      action:'genesis_epoch'|'add'|'remove'|'rekey'|'reshare',
      targetParticipantId?, targetScreenName?,
      signerId, signerSigningPublicKey, signerScreenName, timestamp,

Transition validity -- ALL must hold                                    [PR-04]
    a. signature verifies and signerId === SHA-256(signerSigningPublicKey)
    b. parentPacketId + parentKeyId name a locally validated epoch head,
       or, for action 'genesis_epoch', name the genesis packet
    c. epoch === parent.epoch + 1, except action 'reshare' where
       epoch === parent.epoch and keyId === parent.keyId
    d. signer was a member of the PARENT epoch
       (for 'genesis_epoch': signer === genesis.creatorId)
    e. action 'add'    : members === parent.members + {target}, exactly
       action 'remove' : members === parent.members - {target}, exactly
       action 'rekey'  : members === parent.members, exactly
       action 'reshare': members === parent.members, no epoch change
    f. 1 <= members.length <= MAX_PRIVATE_MEMBERS_HARD (128), no duplicates.
       This is a structural bound from the envelope size limit, NOT a
       membership policy -- see [L-17].
    g. keys has exactly one slot per member, no extra slots
    h. reshare is only valid for a participant already listed in that epoch

Fork resolution                                                         [PR-05]
    Two valid children of the same parent -> the child with the
    lexicographically greatest packetId is canonical. Retain observed forks in
    `membershipHeads` for audit; adopt only the canonical branch. A later
    transition must name the canonical head. The UI should disable local approve
    while a transition is in flight, as a reduction not a replacement.

Storage: `membershipHeads` store, one record per convId, holding the validated
chain (epoch -> {packetId, keyId, members, signerId, timestamp}), the canonical
head, and observed forks.

[X-08] Capability rotation on removal -- [PR-07]
--------------------------------------------------------------------------------
CapabilityRotationPacket (NEW)
    { type:'capability_rotation', protocol, convId, packetId,
      generation: number,                  // increments per rotation
      newEpoch, newKeyId, parentPacketId, parentKeyId,
      removedParticipantId,
      members: string[],                   // the remaining members, sorted
      wrapped: Record<participantId, base64url RSA-OAEP(JSON{
                  roomSecret: string, epochKey: string })>,
      signerId, signerSigningPublicKey, timestamp, signature }
    Signed AIRTHREAD_CAPABILITY_ROTATION_V3:.

Flow:
    1. Remover generates a fresh 256-bit roomSecret AND a fresh epoch key.
    2. Derives the new root/routing/webrtc values from the new secret.
    3. Builds the rotation packet, wrapping {newRoomSecret, newEpochKey} to each
       remaining member's RSA public key.
    4. Publishes it as a control envelope UNDER THE OLD ROOT KEY on the OLD
       routing tag, so offline members find it where they are already looking.
       The removed member can see the event but has no wrapped slot.
    5. Publishes genesis verbatim onto the NEW routing tag [L-05], then
       switches all publishing and subscriptions to the new tag.
    6. Keeps a read-only subscription to the OLD tag for
       OLD_ROUTE_MONITOR_MS (30 days), accepting ONLY rotation packets there.
       No chat is accepted on a rotated-away route.
    7. Revokes outstanding invitations for the old secret; new invitations carry
       the new secret and the new generation.

Receiver side: validate the chain step as a 'remove' transition, unwrap the
slot, adopt the new secret, recompute derivations, resubscribe, bump the stored
capability generation, and rewrite the room record + invite URL.

An invite whose capabilityGeneration is older than the room's current generation
is rejected even if its Nostr event is still stored.                     [N-04]

This closes v2 [O-05].

[X-09] RelayPool contract -- src/services/nostr/relayPool.ts
--------------------------------------------------------------------------------
One singleton. NIP-01 client verbs: EVENT, REQ, CLOSE inbound; EVENT, OK, EOSE,
CLOSED, NOTICE outbound handling.

    class RelayPool {
      configure(urls: string[]): void            // hot-swappable [T-01]
      getHealth(): RelayHealth[]                 // [A-01]
      subscribe(spec: SubscriptionSpec): Subscription
      publish(event: NostrEvent, opts?): Promise<PublishResult>
      close(): void
    }

    interface RelayHealth {
      url: string
      connected: boolean      // socket open
      writable: boolean       // a recent EVENT got OK
      readable: boolean       // a subscription produced EOSE or events
      rttMs: number | null
      lastEventAt: number | null
      backlog: number
      lastError: string | null
    }

    interface PublishResult {
      eventId: string
      accepted: string[]      // relay urls that returned OK true
      rejected: {url, reason}[]
      failed: string[]        // timeout / socket error
      quorumMet: boolean
    }

Rules:
    - Only a positive OK naming the exact event id counts as acceptance.
      Socket-open is NOT delivery.                            [T-07][PU-03][O-12]
    - A relay rejection (OK false) is recorded distinctly from a network failure.
    - Retry re-sends the byte-identical signed event with the same packetId.
    - Subscriptions are multiplexed: many routing tags per REQ where the relay
      allows it, split into bounded batches otherwise.                  [T-08]
    - Reconnect recreates subscriptions with `since` = last committed timestamp
      for that (relay, routingTag) minus an overlap window, from the
      `relayCursors` store.                                             [T-08]
    - Tolerate a relay refusing the configured kind: drop that relay from the
      working set for that subscription, keep the rest.                 [T-02]
    - Token buckets per room-scoped pubkey, senderId, routingTag and packet
      class on the INBOUND side, to bound abuse.                        [A-02]

Outbox (src/services/nostr/outbox.ts):
    Every publish is written to the `nostrOutbox` store BEFORE the socket write
    [D-01 step 3]. State machine: pending -> relayed | failed.
    Retry loop with exponential backoff + jitter, capped attempts, survives
    reload, cancellable while still pending.                            [A-05]

9. RISKS AND GOTCHAS
================================================================================

[G-01] Unique `d` tag per packet is unusual for NIP-33
    [T-03] gives every immutable room packet its own `d`, which means one stored
    parameterized-replaceable event per chat message. Some relays cap the number
    of such events per pubkey or treat kind 30078 specially. Test early against
    the real default relay set -- this is the single assumption most likely to
    fail in the field. If a relay refuses, [T-02] already requires continuing
    with the rest of the set; make sure that path actually works before phase 3
    depends on it. If it fails broadly, the fallback is a regular (non-
    replaceable) kind for immutable packets, keeping replaceable kinds only for
    presence/descriptors/outbox -- treat that as a phase-2 finding, not a
    phase-8 surprise.

[G-02] Public relays will rate-limit a chat application
    Every message is now a relay write. The default relays are community-run and
    tuned for social posting. Expect throttling on bursts. The outbox retry and
    the [A-02] token buckets are what keep this civil; do not remove them for
    convenience during development, and do not test with tight loops against
    public relays.

[G-03] Epoch-chain rebuild depends on relays keeping control packets
    [L-05]/[L-06] omit the expiration tag on control packets, but a relay may
    still prune. The local `membershipHeads` store is the durable copy, and a
    member who has never seen the chain and finds no control packets on any
    relay simply cannot join -- they must be re-invited. Make that failure
    explicit in the UI rather than a silent empty room.

[G-04] The removal rotation has a delivery window
    An offline member who never retrieves the rotation packet within
    OLD_ROUTE_MONITOR_MS is stranded and must be re-invited. Surface this: after
    a rotation, show which members have and have not adopted the new generation.

[G-05] Losing the identity keypair is now more consequential
    Presence capabilities, room secrets and epoch keys all hang off the profile.
    Combined with [C-02] deleting the old database, be very sure the new-profile
    path is correct before shipping, and keep the existing profile export/import
    working.

[G-06] Two send paths, one dedup ledger
    [P-03] requires the byte-identical envelope on both transports. Any
    re-serialization difference (key order, number formatting) between the Nostr
    path and the WebRTC path produces a different contentHash and a spurious
    collision. Serialize ONCE and pass the string to both.

[G-07] Clock skew
    [D-04] rejects packets more than 5 minutes in the future. A user with a badly
    set clock becomes invisible. Log rejections with the delta so this is
    diagnosable, and consider a one-line UI warning if many packets are rejected
    for skew.

[G-08] The single-file build
    Everything ends up inlined in docs/index.html. Watch the bundle size as the
    new services land; `assetsInlineLimit` is effectively unbounded, so nothing
    will warn.

[G-09] Do not regress the comic layer
    Nothing in src/comic/ should change. If a type change in src/types/index.ts
    ripples into it, adapt at the boundary rather than editing the comic code.
